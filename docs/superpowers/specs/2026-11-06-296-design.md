# #296: management host must not be an anonymous GitHub proxy

## Problem

The management host registers `/api/v3/` and `/api/graphql` on its mux and
sends them to the API proxy handler (`internal/server/server.go`). For a
request with no `ghx_`/`gha_` token the proxy handler forwards it to
api.github.com as-is. An anonymous request, or a request with a raw native
token that the border policy does not block, therefore reaches GitHub
through the management host. The instance becomes an open GitHub proxy that
shares its egress rate limit (seen live: 403 "API rate limit exceeded" for
the egress IP).

## Decision

Wrap the two management-host routes in a new middleware,
`proxy.RequireGHPToken`. It runs before the proxy handler and uses the same
`extractClientToken` parser:

| Request | Result |
|---|---|
| `ghx_`/`gha_` token (bearer, token or basic `x-access-token`) | passed to the proxy handler unchanged |
| no usable credential (no header, or a header that does not parse) | 401, `WWW-Authenticate: Bearer`, message "Authentication with a GHP-issued token (ghx_ or gha_) is required" |
| any other credential (native `gho_`/`ghp_`/`ghs_`/`github_pat_`, or an unknown string) | 403 |

For the 403, when the border policy also blocks the token type the body
keeps the existing message "Token type is not permitted by the border
policy" so current clients and the BORDER-C43 rig scenarios see no change.
Otherwise the message is "Native GitHub tokens are not accepted on the GHP
management host; use a GHP-issued token (ghx_ or gha_)". The status is 403
in both cases, independent of the `block.*` settings.

The api.github.com virtual host is not changed: the border policy and
transparent pass-through still govern it.

No config option. There is no documented client that needs anonymous or
native-token access to the management host's GHES-style paths: GHES-style
clients (gh with `GH_HOST`, Octokit with a base URL) always send a token,
and an operator who wants raw pass-through can use the api.github.com
virtual host, where the border policy applies. Default and only behaviour
is deny.

## Metrics

- New counter `ghp_management_host_rejected_total{reason}` with
  `reason` in `anonymous`, `native_token`.
- The decision is timed under the existing `border_policy_check` stage
  (`token_type="unknown"`), and `total` is recorded for rejected requests,
  as the proxy handler does for its own early rejections.

## Tests

- `internal/proxy`: table-driven middleware test for anonymous, unparseable,
  native (blocked and not blocked), basic auth with a native password, and
  `ghx_`/`gha_` on both `/api/v3/user` and `/api/graphql`, asserting status,
  message, that the next handler is or is not called, and the counter.
- `internal/server`: route-level test that the management mux returns 401
  for an anonymous `/api/v3/user` and `/api/graphql`.
- `internal/metrics`: counter test.

## Rig

Two new scenarios under the new claim `MISC-C55` ("The management host's
GHES-style API paths require a GHP-issued token"): anonymous `GET /user`
and anonymous `POST /graphql`-equivalent are both 401. A rest scenario with
`headers: {Authorization: ""}` overrides the profile token, so the request
reaches the server with an empty Authorization header.
