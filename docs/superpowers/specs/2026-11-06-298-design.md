# #298: classify the GraphQL fields gh 2.102.0 sends

## Problem

For permission-scoped tokens the analyzer denies object fields that are in
no table. `gh` 2.102.0 sends 29 such names, so most read commands fail with
"unmapped fields".

## Design

Add each name to one table, field name only, stricter scope when unsure.

- alwaysAllowedFields (metadata only): `node` (Edge.node; root `node(id:)`
  is still a gated lookup and cross-repo), `author`, `assignees`, `users`,
  `requestedReviewer`, `enabledBy` (actors under a gated parent),
  `fields`, `enumValues` (introspection under `__type`).
- fieldScopeRequirements:
  - issues:read: `labels`, `milestone`, `comments`, `issueType`,
    `subIssues`, `subIssuesSummary`, `blockedBy`, `blocking`, `parent`.
  - pull_requests:read: `autoMergeRequest`, `headRepository`,
    `headRepositoryOwner`.
  - contents:read: `commits`, `baseRef`.
  - checks:read: `contexts`, `checkRunCountsByState`.
  - statuses:read: `statusContextCountsByState`.
  - actions:read: `workflow`.
  - projects:read: `projectItems`, `fieldValueByName`.
  - metadata:read: `repositories` (stays in crossRepoAnywhereFields).
- Not added: `args`, `type`, `ofType` (no capture shows gh sending them).

## Deferred (operator ruling)

`parent`, `headRepository`, `headRepositoryOwner`, `subIssues`,
`blockedBy`, `blocking` can reach other repositories. They are not added
to the cross-repo tables in this change; this is a documented known
limitation with a planned follow-up that restricts selections under them.

## Corpus and rig

Every #298 known issue in `rig/corpus/gh/2.102.0` is resolved. Cells
where the perm-ro profile lacks a scope the query now needs (checks,
statuses, administration, projects) take the verdict
`deny:missing_scope`. The two introspection probes take `deny:no_repo_ref`
for the repo profile. GH-C51 scenarios that now pass drop `known_issue`;
the rest keep it with the reason.

No new decision point, so no metrics change.
