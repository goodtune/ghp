# #292: scope enforcement for github.com non-git paths and codeload

## Problem

On the github.com virtual host, `NewScopedPassthroughHandler` checked scopes
only for git smart-HTTP paths. Any other path (archive downloads, release
asset downloads, `.git/` suffixes other than the smart-HTTP endpoints,
`info/refs` without a known `service`) resolved the client token to the real
GitHub credential and forwarded it with no repository or permission check.
The codeload.github.com handler never resolved client tokens, so a raw
`ghx_`/`gha_` string was sent upstream.

Live run 20261105T0534Z, GAP-A3: a repo-A token fetched
`/{B}/archive/HEAD.tar.gz` on the github.com vhost. GHP did not deny it;
GitHub answered 404.

## Decision: deny by default

For scoped client tokens (repository and/or permission restrictions):

| vhost | path | method | repo | permission |
|---|---|---|---|---|
| github.com | git smart HTTP (unchanged) | as before | `{o}/{r}` | contents:read/write |
| github.com | `/{o}/{r}/archive/...` | GET, HEAD | `{o}/{r}` | contents:read |
| github.com | `/{o}/{r}/releases/download/...` | GET, HEAD | `{o}/{r}` | contents:read |
| codeload.github.com | `/{o}/{r}/{tar.gz,zip,legacy.tar.gz,legacy.zip}/{ref}` | GET, HEAD | `{o}/{r}` | contents:read |
| either | anything else | any | - | unmapped: 403 |

The mapped request then goes through the same repository allowlist and
permission checks as git smart HTTP. An unmapped path is denied with a 403
that names the reason, even when the token has only a repository restriction:
GHP cannot prove the path stays inside the allowlist.

Open-scoped tokens (no repos and no scopes) keep the old behaviour: resolve
and forward. Requests without a client token are unchanged.

## Codeload

`NewScopedCodeloadHandler` wraps the whole codeload handler (redirect and
passthrough) with the same scoped handler, with codeload's path mapping. The
client token is resolved and replaced with the real credential before the
forward, so a `ghx_` string never goes upstream. The scope check runs before
the mirror redirect too, so a token cannot use a redirect to learn about an
out-of-scope repository. The enterprise policy and the border policy are not
applied on codeload (unchanged).

## Metrics

`ghp_passthrough_scope_denied_total{vhost, reason}` with reason in
`unmapped`, `repo`, `permission`. Decision time stays under the existing
`scope_enforcement` stage.

## Code layout

- `internal/proxy/webscope.go` (new): `GitHubWebScope`, `CodeloadScope`.
- `internal/proxy/passthrough.go`: `NewScopedPassthroughHandler` body moved
  into `newScopedWebHandler`, parametrised by vhost and mapper;
  `NewScopedCodeloadHandler` added.
- `internal/proxy/scope.go`: not touched.

## Known limitation

The releases handler (`releases.mode: redirect|block`) runs before the scope
check, so an out-of-scope release download in redirect mode still receives a
302 to the operator mirror (no credential is forwarded to GitHub).
