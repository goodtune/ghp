# Design: REST and permission-name correctness (#315, #316, #318)

## #315 Reactions

Rules in `internal/proxy/scope.go`, placed ahead of the area catch-alls:

| Endpoint | GET | POST / DELETE |
|---|---|---|
| `issues/{n}/reactions`, `issues/{n}/reactions/{id}` | `issues:read` | `issues:write` |
| `issues/comments/{id}/reactions[/{id}]` | `issues:read` | `issues:write` (already covered by the `issues/comments/{id}/*` rules; tests added) |
| `pulls/comments/{id}/reactions[/{id}]` | `pull_requests:read` | `pull_requests:write` (already covered by the `pulls/comments/{id}/*` rules; tests added) |
| `comments/{id}/reactions[/{id}]` (commit comments) | `contents:read` | `contents:write` |

## #316 Actions workflows

GitHub documents the workflow endpoints under the Actions permission
(list/get: read; enable, disable, dispatch: write). The GitHub App
`workflows` permission has only a `write` level and governs editing
workflow files. Change:

- `actions/workflows*` GET maps to `actions:read`; enable, disable and
  dispatches map to `actions:write`. The GraphQL `workflowFile` field moves
  from `workflows:read` to `actions:read`.
- Compatibility alias for one release: `workflows:read` is still accepted by
  the validator. It logs a deprecation warning at creation and is treated as
  `actions:read` for enforcement. On the agent (`gha_`) path it is sent to
  GitHub as `actions:read`. `workflows:write` is unchanged (it is the
  workflow-file edit permission) and does not imply `actions:read`.

## #318 Permission names

1. `projects` stays as the enforcement name used by the GraphQL Projects v2
   tables and the classic REST project rules. Enforcement treats a
   `projects:<level>` requirement as satisfied by `projects`,
   `repository_projects` or `organization_projects` at that level. On the
   agent path, `projects:<level>` is translated to `repository_projects` and
   `organization_projects` at that level (the higher level wins when the
   token also names those keys), so the access_tokens request never carries
   a `projects` key.
2. Add the missing repository and organization App permission names. Source:
   the `app-permissions` schema in GitHub's REST description
   (https://github.com/github/rest-api-description, schema
   `components.schemas.app-permissions`), which backs the `permissions`
   body of "Create an installation access token for an app"
   (https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app)
   and the page https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps.
   Added: `artifact_metadata`, `attestations`, `code_quality`,
   `merge_queues`, `custom_properties_for_organizations`,
   `enterprise_custom_properties_for_organizations`,
   `organization_announcement_banners`, `organization_copilot_agent_settings`,
   `organization_copilot_requests`, `organization_copilot_seat_management`,
   `organization_custom_org_roles`, `organization_custom_properties`,
   `organization_events`, `organization_external_properties_for_repos`,
   `organization_personal_access_token_requests`,
   `organization_personal_access_tokens`.
   Not added: account (user) permissions (`email_addresses`, `followers`,
   `git_ssh_keys`, `gpg_keys`, `interaction_limits`, `profile`, `starring`);
   installation tokens act on an installation, not a user account.
   Kept although absent from the schema: `variables` and `team_discussions`
   (existing names; removing them would invalidate stored tokens).
   The `admin` level that some names accept is not added: GHP levels stay
   `read`/`write`.

## Placement

Alias logic lives in `internal/permissions` (`Grants`, `ForGitHubApp`) so
`database.Scopes.HasPermission` and the agent mint path share one table.
No new decision points: the alias check runs inside the existing
`scope_enforcement` timing.
