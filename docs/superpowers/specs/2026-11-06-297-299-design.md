# #297 / #299: gh-friendly GraphQL repository pinning and `__typename` at a mutation root

Status: policy change. The operator must sign off before merge.

## Problem

- #297: gh sends every repository query as
  `repository(owner: $owner, name: $name)` with the values in the request's
  `variables` object. The analyzer accepts only literal string arguments, so
  it sets `hasUnpinnedRepositoryLookup` and every gh query fails with 403 for
  a repository-scoped token.
- #299: a mutation that selects `__typename` at the operation root is denied
  as an unmapped mutation, although `__typename` returns only the type name
  `Mutation` and changes nothing.

## Rule for #297 (exact)

A `repository(...)` field with arguments is *pinned* to `owner/name` only when
all of these are true. Otherwise it is *unpinned*, as before.

1. The arguments are exactly `owner` and `name` (current behaviour).
2. Each argument is either a literal GraphQL string, or a variable reference
   `$v` where:
   - the selected operation declares `$v` with the named type `String`
     (nullable or non-null, not a list);
   - the request body has a top-level `variables` member that is a JSON
     object, and that object has the key `v`;
   - the value of `v` is a JSON string. `null`, numbers, booleans, arrays,
     objects and a missing key are unpinned.
3. The operation-level default value (`$v: String = "x"`) is never used. If
   the key is not in `variables`, the lookup is unpinned.
4. The request body has no duplicate keys at the top level, and the
   `variables` object has no duplicate keys. If any duplicate exists, no
   variable is resolved (all variable-driven lookups are unpinned). This
   stops parser differentials, where the proxy and GitHub take different
   values for the same key.
5. The document has exactly one operation. If it has more than one, no
   variable is resolved, even with `operationName`.

All other policy is unchanged: cross-repository fields, mutations for
repository-scoped tokens, the allowlist check on every pinned repository,
and the requirement for at least one pinned repository.

## Why it is safe

- The analysed bytes are the forwarded bytes. `handleGraphQL` buffers the
  body once, analyses that buffer, and replays the same buffer upstream.
  A handler test asserts byte equality of the upstream body.
- GraphQL has one value per variable per request. GitHub substitutes the
  value from `variables`, so the resolved string is the value GitHub uses.
  Default values are ignored, so a value that GitHub could take from a place
  the proxy does not read cannot exist.
- The type check (`String`) means that GitHub does no coercion that the proxy
  does not see. A JSON string to a `String` variable is used as is.
- Duplicate keys and multiple operations are the remaining places where the
  proxy and GitHub could disagree about the value. Both fall back to
  unpinned (deny for repository-scoped tokens).
- Nested accessors such as `headRepository` or `baseRepository` are not
  `repository` lookups. Where they are cross-repository they stay in the
  cross-repository tables. A nested `repository(owner: $o, name: $n)` is
  pinned by the same rule as a root one, and then checked against the
  allowlist.

## Rule for #299

At a mutation root, `__typename` is metadata with no scope requirement. All
other mutation root fields still need their entry in
`mutationScopeRequirements`. A mutation that selects only `__typename`
has no write scope, so a permission-scoped token still gets
`deny:mutation_unscoped`; a repository-scoped token still gets
`deny:mutation_repo`.

## Metrics

No new decision point. The variable resolution runs inside
`analyzeGraphQLRequest` and is timed by the existing `graphql_analysis`
stage.
