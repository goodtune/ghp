# GraphQL cross-repo gating: metadata-only subtrees, parent-aware issues/pullRequests, introspection-only operations (#339, #340, #342)

## Problem

- #339: `headRepository`, `headRepositoryOwner`, `parent` (Repository.parent and Issue.parent), `subIssues`, `blockedBy` and `blocking` can return objects from repositories outside the allowlist, but the analyzer only scope-maps them. A repo-A token can read `pullRequest{headRepository{issues{nodes{body}}}}`.
- #340: `User.issues` / `User.pullRequests` (via `viewer`, `author{...on User}`, `assignees`, `owner`) span every repository the credential can see. The analyzer matches by name only and allows them.
- #342: gh sends introspection-only probes (`PullRequest_fields2`, `Release_fields`, `SearchType_enumValues`). A repository-restricted token is denied with deny:no_repo_ref although no repository data is selected.

## Design

The walk carries a small context value (`walkCtx`): the immediate parent field name, whether that parent is a pinned `repository(owner, name)` lookup, and the name of the enclosing metadata-only subtree (if any). Fragments are transparent: they pass the context through unchanged.

1. Metadata-only subtree (`metadataOnlySubtreeFields`: headRepository, headRepositoryOwner, parent, subIssues, blockedBy, blocking). The field itself keeps its scope. Beneath it, a selection must be in `alwaysAllowedFields`, or be a scalar leaf in `metadataSubtreeLeaves` (`number`, `state`, `title`). Anything else records a cross-repo field `<subtree>.<field>` (e.g. `headRepository.issues`). Normal scope and unmapped classification still runs, so permission-only tokens are unaffected. `metadataSubtreeLeaves` exists because `gh issue view` selects `parent{id,number,title,url,state,repository{nameWithOwner}}` and the same shape under subIssues/blockedBy/blocking; the operator requires `gh issue view` to keep working for repo-A. The trade-off (number, title and state of a linked issue in another repository are disclosed) is documented.
2. Parent-aware cross-repo (`crossRepoParentAwareFields`: issues, pullRequests, issueComments, commitComments). Cross-repo unless the immediate parent is a pinned `repository(owner, name)` field. `repositories` is already in `crossRepoAnywhereFields`.
3. Introspection-only operations. The analysis records `introspectionOnly` when every root selection (fragments expanded) of a query is `__type`, `__schema` or `__typename`. graphQLVerdict skips the repository-reference requirement for such operations only. Every other check still runs.

All three rules only add cross-repo entries or relax no_repo_ref for a narrow shape, so deny-by-default is unchanged. No new metric: the work is inside `graphql_analysis`.

## Corpus impact

- `release_list` Release_fields and `search_prs` SearchType_enumValues: repo deny:no_repo_ref -> allow.
- `pr_create_dryrun` RepositoryInfo: repo allow -> deny:cross_repo (`parent{...repo}` selects `viewerPermission`). gh pr create already needs a mutation, which repository-restricted tokens cannot send.
- `issue_view`, `pr_view`, `pr_list`, `issue_list`, `pr_checks` PullRequestByNumber: unchanged.
